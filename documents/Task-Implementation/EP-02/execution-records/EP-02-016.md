## 1. Implementation summary

**Request**
- `admin.request_verification_override(actor, case, requestedState, reason)` requires
  `admin.verification.review`, a reason of at least five characters, a state of `APPROVED` or
  `REJECTED`, and a `verification_review` case;
- it refuses a second pending request for the same case;
- it writes one `approval_requests` row (`action_type = verification_override`,
  `target_type = verification_case`, `requested_state`) and one step requiring
  `admin.approval.decide`.

**Decision**
- `admin.decide_approval` gains the `verification_override` branch:
  - the approvals spine already refuses a self-decision (`42501`) and a second decision;
  - the approver must also hold `admin.verification.review`;
  - on approval the review case is resolved to its submission, the lane case is reached through it,
    and the lane and its latest submission move to the requested state;
  - the transition table is bypassed **only** inside this function, through a transaction-local
    `app.verification_override` marker that the trigger checks. Nothing else can set it;
  - one decision row records the approver, the requester, the reason, the prior and next state and
    the evidence ids;
  - on rejection nothing changes: the approval is marked rejected and the lane keeps its state.

**API**
- `POST /v1/control/verification/{id}/override` with `{ requestedState, reason }`, control audience,
  201 with the approval request;
- the existing approval decision endpoint records the second operator's decision; no second endpoint
  was added for that.

**Both actors**
- the request carries `requester_user_id`; the decision carries `decided_by` and `requested_by`, plus
  `admin_case_id` pointing at the review case and `case_id` at the lane case.

## 4. Design decisions

| Decision | Reason |
|---|---|
| Reuse the approvals spine | Self-approval refusal, one-pending rule, steps and decisions already exist; a parallel model would drift. |
| Target the review case, resolve the lane through the submission | The approval names what a human reviews; the lane case is an implementation detail. |
| Transaction-local marker for the bypass | An override must step past the transition table, and only this function may do it; a session GUC cannot leak across transactions. |
| Approver needs both permissions | Approving a lane decision is still a verification act; `admin.approval.decide` alone is not enough. |
| Rejection is a true no-op | R-07 requires it; the request row records the attempt. |
| One decision row per executed override | The immutable record is `profile.verification_decisions`, not the approval row. |

## 9. Outstanding issues

- **No control-portal button.** The endpoint and the approvals list exist; the verification screen does
  not yet offer "request override". That is a `CP-019` UI change.
- **The override moves the lane, not the tier.** An approved override of the `kyc` lane does not
  change `identity.accounts.kyc_tier`; tier changes remain with the reviewer decision in `EP-02-015`.
  If an override must correct a tier, that is a separate decision.
- **One approval step.** The spine is single-stage: one second operator, not two sequential approvers.
- **No notification** to the requester or the subject.
- **The bypass is a GUC.** It is transaction-local and set only by `decide_approval`; a future
  function could misuse it, so the convention is recorded here rather than assumed.

## 10. Final status

**`COMPLETED`** — a decided lane can be corrected only through a two-person approval that records both
actors, the reason and the state change, and a rejected override changes nothing.
