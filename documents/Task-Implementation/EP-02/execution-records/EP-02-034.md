## 1. Implementation summary

A repeated money request now returns the original result, and a changed request under the same key is
refused.

**Platform idempotency store** (`server/src/modules/platform/idempotency.ts`)
- `claimIdempotency` inserts the key with `on conflict do nothing`; an existing row is locked with
  `for update`, so a concurrent retry waits for the first transaction and then reads its response;
- the same request hash returns the stored response; a different hash is a conflict; a committed
  record with no response is an internal error, never a silent replay;
- `completeIdempotency` stores the response inside the same transaction as the ledger write.

**Ledger keys** (`server/src/modules/finance/idempotency.ts`, `LedgerService`)
- every `postEntry` now requires an idempotency key;
- the stored key is scoped as `finance.ledger.post:<accountId>:<client key>`, so two accounts may use
  the same client key;
- the request hash canonicalises amounts (`100.1` = `100.1000`), whitespace and posting order, so a
  formatting retry replays;
- any change to an account, amount, direction, currency, kind, reference, activity or reversal target
  changes the hash and is a conflict;
- the record's expiry is `infinity`: a money key must never become reusable;
- a replay does not insert an entry, postings or an audit row a second time.

**Per-creator uniqueness** (migration)
- the old global unique index on `journal_entries.idempotency_key` is replaced with
  `(coalesce(created_by, nil uuid), idempotency_key)`, so two creators can use the same key while one
  creator cannot.

**Provider references** (`ProviderReferenceService`, migration)
- each reference now belongs to an account and remains unique per `(provider, provider_reference)`;
- recording the same event returns the first record with `replayed: true`; a different amount,
  currency, direction or account under the same reference is a conflict;
- linking sets `status = 'posted'` and `journal_entry_id`; a repeated link to the same entry is a
  no-op, a different entry is a conflict, a currency mismatch is refused, and an invisible entry is
  not found;
- only `status`, `journal_entry_id` and `updated_at` are update-granted; provider, reference, amount,
  currency and account are immutable after recording;
- RLS scopes the row to its owning account until it is linked to an entry the caller can see.

## 3. Design decisions

| Decision | Reason |
|---|---|
| Claim before the reversal lookup and posting | The expensive and side-effecting work only runs for the transaction that owns the key. |
| `on conflict do nothing` then `select … for update` | It makes a concurrent retry wait and replay rather than race into a duplicate posting. |
| Canonical hash over money values, not input bytes | Formatting and posting order are not part of the movement; a changed value is. |
| Key scoped by account in the stored string | Two accounts can pick the same human key without colliding; the journal index is per creator as a second line. |
| Expiry `infinity` | A second movement after a timeout is still a second movement. |
| Provider reference account column | A reference must be owner-scoped for RLS; it also lets an unlinked event be read by its payer. |
| Amount is immutable after recording | A changed amount under the same provider reference is a different event and is refused, not patched. |
| Link checks currency only | Amount matching depends on fee and split rules that are not approved; the adapter tasks own that comparison. |
| No delete path for provider references | They are the evidentiary trace of a provider event. |
