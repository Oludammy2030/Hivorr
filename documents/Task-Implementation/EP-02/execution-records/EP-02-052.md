## 1. Implementation summary

**Posting** (`server/src/modules/finance/deposit-posting.service.ts`)
- the provider reference is inserted into `finance.provider_references` with
  `on conflict (provider, provider_reference) do nothing`. The insert is the claim; a loser re-reads
  the row `for update`;
- a replayed reference with a journal entry returns `replayed` and posts nothing;
- a reference already marked failed returns `blocked` with `kyc_upgrade_required`;
- a reference reused for a different account, direction, currency or amount is `CONFLICT`;
- the account's KYC tier is read inside the transaction, then `DepositEligibilityService` applies the
  CBN single-deposit cap. A refusal marks the reference failed and returns `blocked` without a credit;
- `ensure_ledger_account` provisions the wallet and `platform_clearing` in the same transaction;
- `LedgerService.postEntryInTransaction` writes one balanced entry: wallet debit, clearing credit,
  with idempotency key `deposit:<provider>:<reference>`;
- the reference is marked posted with the journal entry id, and `finance.deposit_posted` is audited in
  the same transaction.

**Why the entry balances**
- the wallet view derives a balance as `sum(debit) - sum(credit)` over postings, so a wallet debit is
  an increase to the user. Clearing receives the matching credit. The task's wording ("debits
  provider clearing and credits the user wallet") describes the same movement from the platform's
  side; the ledger convention is the one enforced by `EP-02-030`/`031` and asserted by the database
  gate.

**Error surface**
- `42501` from the database is `FORBIDDEN`; `23505`/`23514` are `CONFLICT`; anything else is rethrown
  as-is rather than swallowed.

## 3. Rules

| Situation | Result |
|---|---|
| First receipt of a verified deposit within the cap | posted once, reference `posted`, audit written |
| Replay of a posted reference | `replayed`, no second entry, no second audit |
| Replay of a held reference | `blocked`, `kyc_upgrade_required` |
| Reference reused with a different amount, currency, account or direction | `CONFLICT` (409) |
| Tier below `tier_1` | `blocked`, `kyc_required`, reference marked failed |
| Amount above the tier's single-deposit cap | `blocked`, `kyc_upgrade_required`, hold set by the gate |
| Database permission denial (`42501`) | `FORBIDDEN` (403) |
| Unique or check violation (`23505`/`23514`) | `CONFLICT` (409) |

## 4. Design decisions

| Decision | Reason |
|---|---|
| Insert-then-read claim | A unique constraint is the only reliable exactly-once control under concurrency; a read-then-insert races. |
| `for update` on the losing row | Serialises replays so two concurrent deliveries cannot both post. |
| Eligibility inside the transaction | The tier and the cap are read at posting time; a cached tier could post an over-cap deposit. |
| Mark failed rather than delete | The provider reference is evidence; the hold and the failure must both be reconstructable. |
| Audit inside the transaction | The ledger entry and its audit commit or roll back together. No orphan evidence. |
| Amount as the canonical string | `numeric(20,4)` end to end; no float, no rounding. |

## 9. Outstanding issues

- **Payer-name matching is absent.** `EP-02-051` is an open decision; until it is made, a deposit is
  owned by its collection account alone. `AGENTS.md` Rule 3 states the rule, so this is a known gap
  between policy and code.
- **An over-cap deposit is not recovered.** The credit stays unposted after the tier is raised; the
  provider reference remains failed. Recovery needs a decision and belongs to `055`.
- **No reconciliation.** An unmatched credit is not surfaced anywhere yet.
- **No sandbox certification.** No Paystack test key is present.
- **No asynchronous retry.** A posting failure surfaces to the webhook caller; the provider retry is
  the only recovery.
