## 1. Implementation summary

**Transition table** (`server/src/modules/profile/domain/verification.ts`)
- seven states and one table, identical for all six lanes: a lane is not an account status and
  approving one never implies another;
- `APPROVED` has a single exit, `EXPIRED`; it never returns to draft or submitted. Rejection and
  expiry are the only reopenable states;
- submissions use the same table minus `NOT_STARTED`, so a submission cannot be born started;
- subject events are explicit: `start` from not-started/rejected/expired, `submit` from draft,
  `withdraw` from submitted. Under review is not withdrawable — the reviewer owns the row then.

**Database enforcement** (`20261127000400_profile_alter_verification_transitions.sql`)
- `profile.verification_transition_allowed(from, to)` is the same table in SQL, so a direct update
  cannot skip the domain;
- a before-update trigger on `profile.verification_cases` and `profile.verification_submissions`
  raises `23514` on an unapproved edge;
- the freeze predicate `profile.identity_fields_are_frozen(account)` is security-definer, so the
  writer's RLS cannot narrow it;
- a trigger on `profile.profiles` refuses a change to `display_name` or `avatar_url` while any
  submission for the account is under review. `bio`, `locale` and `timezone` stay editable.

**Submission domain** (`server/src/modules/profile/verification.service.ts`)
- `start`: creates the case if absent, moves it to draft, opens one draft attempt. Refused while an
  attempt is open and while the lane is approved;
- `submit`: requires at least one evidence reference and refuses any evidence whose scan state is
  `INFECTED` or `FAILED`; moves submission and case to submitted in one transaction;
- `withdraw`: submitted back to draft, refused while under review;
- `status`: the lane's state, whether an attempt is open and how much evidence it carries;
- every change is audited with the lane and the from/to states.

**Not duplicated**
- no second lane vocabulary: the shared contract and `profile.verification_lanes` remain the source;
- no capability was invented. Only `business.verification.submit` exists in the shared vocabulary, so
  the service does not gate lane submissions on a capability it would have had to invent; `EP-02-013`
  owns that decision;
- the service is not registered in `AppModule` because nothing exposes it yet; `EP-02-013` wires it.

## 3. Rules

| Situation | Result |
|---|---|
| Start from `NOT_STARTED`, `REJECTED` or `EXPIRED` | draft attempt opened, audited |
| Start while another attempt is open | `CONFLICT` (409) |
| Start on an `APPROVED` lane | `CONFLICT` (409); approval is never silently reopened |
| Submit with no evidence | `VALIDATION_FAILED` (400) |
| Submit with an `INFECTED`/`FAILED` scan | `VALIDATION_FAILED` (400) |
| Submit while not in draft | `CONFLICT` (409) |
| Withdraw from `SUBMITTED` | back to `DRAFT`, audited |
| Withdraw while under review | `CONFLICT` (409) |
| Withdraw with no open attempt | `NOT_FOUND` (404) |
| Unknown lane | `VALIDATION_FAILED` (400), before any query |
| Any unapproved edge at the database | `23514` |
| Change `display_name`/`avatar_url` while under review | `23514` (`identity_frozen_for_review`) |

## 4. Design decisions

| Decision | Reason |
|---|---|
| One table for every lane | The lanes differ in evidence, not in lifecycle; six copies would drift. |
| Approved exits only to `EXPIRED` | Revocation is a privileged override (`EP-02-016`), not a state edge a subject can reach. |
| Information requests map to `REJECTED` | The shared states have no `INFORMATION_REQUESTED`; inventing one would change an approved contract. `EP-02-015` can use a reason code. |
| Freeze on `display_name` and `avatar_url` only | Those are the identity-bearing columns that exist today; the set grows when the identity-document table lands. |
| Freeze predicate is security definer | Otherwise an owner-scoped RLS policy would answer "not frozen" for a submission they cannot see. |
| No capability gate | The vocabulary has no generic `verification.submit`; inventing one contradicts the reuse rule. |
| Service not in `AppModule` | Nothing calls it yet; wiring it without an endpoint would add an unused provider. |

## 9. Outstanding issues

- **No expiry scheduler.** `SUBMITTED → EXPIRED` and `APPROVED → EXPIRED` are permitted; nothing moves
  a row automatically. A worker job belongs with `EP-02-015`/`055`.
- **Begin-review, approve and reject are not implemented.** The database accepts those edges; only
  `EP-02-015` may apply them, through a reviewer-authorised path.
- **The freeze covers two columns.** It grows when the identity-document table lands (`EP-02-012`).
- **No API.** The service is exported but not registered; `EP-02-013` owns the contract and the
  capability decision.
- **No submission history table.** Submission rows are the history; a superseded attempt keeps its row.
- **Information requests have no state.** They are `REJECTED` with a reason code until the shared
  vocabulary gains one.
