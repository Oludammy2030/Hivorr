## 1. Implementation summary

**Pure domain** (`server/src/modules/finance/limits.ts`)
- resolves the effective rule for a tier or account override: newest `effectiveFrom` wins, a future or
  expired window is ignored, and an account override beats a tier rule;
- denies any tier other than `tier_1` (`tier_0` and a missing tier are `kyc_required`);
- denies when no rule is configured;
- checks per-transaction and daily/weekly/monthly usage, and a wallet-balance cap after the write;
- period starts are UTC (day, Monday, first of month) and the boundary is explicit;
- all comparisons use integer minor units.

**Service** (`server/src/modules/finance/limit.service.ts`)
- `assertWithin(transaction, input)` evaluates on the caller's transaction, so the check and the
  financial write share one snapshot;
- `check(input)` is the read-only variant in its own transaction;
- `setLimit` adds an effective-dated limit, requires `admin.configuration.write` in the service and in
  the database policy, and audits `finance.limit_created` with a mandatory reason;
- `list` returns limits subject to RLS: ordinary accounts see tier rows and their own overrides, a
  configuration writer sees all rows;
- a denial carries the shared stable codes `KYC_REQUIRED` (403) or `LIMIT_EXCEEDED` (403).

**Database** (`20261119000200_finance_add_limit_write_path.sql`)
- insert grant and policy for `finance.limits`, gated on `admin.configuration.write`;
- the select policy also admits a configuration writer;
- no update or delete: a change is a new effective-dated row.

**Nothing is seeded.** No tier threshold, no daily/weekly/monthly value and no wallet cap exists in
code or migrations. The tests use synthetic limits.

## 3. Resolution and denial rules

| Situation | Result |
|---|---|
| `tier_0` or no tier | `KYC_REQUIRED` |
| `tier_1`, no effective rule | `LIMIT_EXCEEDED` — no limit configured |
| `tier_1`, `per_transaction` | amount ≤ limit |
| `tier_1`, `daily`/`weekly`/`monthly` | period usage + amount ≤ limit |
| `tier_1`, `wallet_balance` | balance after the write ≤ limit |
| Account override and tier rule both effective | account override wins |
| Two rules for the same scope | newest `effectiveFrom` wins |

Usage is summed from the append-only postings: deposits count wallet debits with
`journal_entries.kind = 'deposit'`; withdrawals and payouts count wallet credits with the matching
kinds. A reversal carries its own kind and is not counted as new usage.

## 4. Design decisions

| Decision | Reason |
|---|---|
| No threshold in code or seed | The ladder and the numbers are founder decisions; configuration holds them. |
| Only `tier_1` is eligible | That is the approved shared contract; adding a tier requires the ladder decision. |
| Missing tier is treated as `tier_0` | Fail closed when the session cannot prove a tier. |
| `assertWithin` takes a transaction | The check must not run in a second connection from the write. |
| Insert-only limit changes | Effective dating preserves history; an update would erase why a limit applied. |
| UTC period boundaries | The ledger is UTC; a local-timezone rule would be an invented policy. |
| `LIMIT_EXCEEDED` for "not configured" | The shared code set is stable and has no separate code; the message distinguishes the case. |
| Wallet cap uses `available` plus/minus the amount | The cap is a ceiling after the write, not a second stored balance. |
| Limit changes require `admin.configuration.write` twice | Service authority plus a database policy; RLS remains defence in depth. |
