## 1. Implementation summary

**Collections adapter** (`server/src/integrations/paystack/collections.ts`)
- `provisionCollectionAccount` creates a Paystack customer and a dedicated virtual account (DVA),
  returning the provider reference, account number, account name, bank name and currency;
- `normaliseDepositEvent` accepts only `charge.success`, requires a reference and a collection
  account link, and resolves that link from the dedicated account number, then the receiver account
  number, then the customer code;
- the amount arrives in kobo and is converted with `BigInt` through `minorUnitsToMoney`; no float
  arithmetic is used and sub-unit precision is impossible by construction;
- `verifyTransaction` calls `GET /transaction/verify/:reference` and normalises the result through
  the same path, so the webhook and the query share one interpretation;
- failures map to the provider-neutral codes (`PROVIDER_AUTH_FAILED`, `PROVIDER_UNAVAILABLE`,
  `PROVIDER_TIMEOUT`, `PROVIDER_DUPLICATE`, `PROVIDER_REJECTED`, `PROVIDER_NOT_FOUND`,
  `PROVIDER_INVALID_PAYLOAD`) with bounded retry;
- `verifyPaystackSignature` is an HMAC-SHA512 comparison over the raw body, compared in constant
  time. No key, account number or raw payload is logged.

**Collection-account storage** (`supabase/migrations/20261126000200_finance_add_collection_accounts.sql`)
- `finance.collection_accounts` stores one DVA per `(account, provider)` with the owner user, the
  bank-issued number, the name, the bank and the currency. It holds no provider secret;
- row-level security is enabled with owner-scoped select and insert policies; the API role has select
  and insert only, never update or delete;
- `finance.ensure_ledger_account` is extended to provision `platform_clearing`, the counterparty of a
  deposit. Wallet and payout-payable behaviour is unchanged.

**API**
- `GET /v1/wallet/collection-account` returns the caller's own DVA, or null;
- `POST /v1/wallet/collection-account` provisions it through Paystack and audits
  `finance.collection_account_created` with the last four digits only;
- both endpoints are app-audience and session-scoped; the account never comes from the request.

**Provider gate**
- collection provisioning refuses with `SERVICE_UNAVAILABLE` while VFD is the active provider or
  while the active mode has no key. It fails closed rather than guessing.

## 3. Mapping rules

| Situation | Result |
|---|---|
| Paystack customer created, DVA created | stored row with the provider reference and bank details |
| Customer or DVA response missing a required field | `PROVIDER_REJECTED`, nothing stored |
| Account already has a DVA | the stored row is returned; no provider call |
| Active provider is VFD | `SERVICE_UNAVAILABLE`, no provider call |
| Active mode has no secret key | `SERVICE_UNAVAILABLE`, no provider call |
| Concurrent insert wins the unique key | the winning row is returned, no second audit |
| Provider returns `401`/`403` | `PROVIDER_AUTH_FAILED`, no retry |
| Provider returns `429`/`5xx`/timeout | bounded retry, then `PROVIDER_UNAVAILABLE`/`PROVIDER_TIMEOUT` |

## 4. Design decisions

| Decision | Reason |
|---|---|
| Paystack instead of VFD | Founder directive of 26 November 2026; recorded as a scope deviation, not as task completion. |
| One DVA per account and provider | Matches the unique constraint and the funding model; a second account would split deposits. |
| Store the bank-issued number, never a secret | The DVA is public information to its owner; a secret would need encryption and rotation. |
| Owner-scoped RLS plus a service-layer filter | The service supplies the account; RLS filters a second time. Defence in depth is preserved. |
| `platform_clearing` as the deposit counterparty | The ledger must balance; clearing is the named platform account for an inward credit. |
| No sandbox call | No Paystack test key is present in this environment. The adapter fails closed. |
| `PROVIDER_ERROR` at the API edge | A provider failure is not the caller's fault and must not leak provider detail. |

## 9. Outstanding issues

- **VFD collections are not implemented.** The task title names VFD; only Paystack is built. Either
  the task is re-scoped by the founder or the VFD client is written when VFD is resumed.
- **Paystack sandbox certification is not run.** No test key is present; `EP-02-045` owns the evidence.
- **Payer-name matching is not applied.** `EP-02-051` is an open decision; a deposit is matched by the
  collection account, and a payer-name rule would change that path.
- **No card data path exists, by design.** Paystack DVAs accept bank transfers only.
- **The collection account is never rotated.** If Paystack replaces a DVA, the row must be updated
  deliberately; no automatic reconciliation exists yet.
