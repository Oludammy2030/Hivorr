## 1. Implementation summary

Added the read side of the wallet without adding a stored balance.

**Database views** (`20261118000300_finance_create_wallet_views.sql`)
- `finance.wallet_balances` — one row per account and currency: `available`, `pending`, `total`, `withdrawable`;
- `finance.wallet_statement` — one row per wallet posting, with entry id, kind, reference, signed amount, activity attribution and timestamp;
- both are `security_invoker = true`, so the caller's RLS on postings, ledger accounts and escrow accounts applies;
- the posting select policy now also admits postings on an escrow ledger account whose payer is the caller. Without that clause, `pending` would always read zero.

**Read service** (`server/src/modules/finance/wallet.service.ts`)
- `balance(context, currency)` returns zero figures when the account has no ledger history yet;
- `balances(context)` lists every currency the account holds;
- `statement(context, query)` is keyset-paginated newest-first, with optional currency and activity filters, a default page of 50 and a hard maximum of 100;
- the account always comes from the authenticated context, never from a request parameter;
- invalid currency, activity, page size or cursor is refused before any query runs.

**Shared contract**
- `walletStatementEntrySchema` and `signedMoneyAmountSchema` added to `@hivorr/shared`;
- `walletBalanceViewSchema` from `EP-02-002` is the response shape; no second wallet vocabulary exists.

## 2. Figures and their source

| Figure | Definition | Source |
|---|---|---|
| `available` | net of the account's `user_wallet` postings | append-only postings |
| `pending` | net of the postings on the account's escrows whose state is `held` | escrow metadata + postings |
| `total` | `available + pending` | derived |
| `withdrawable` | `available` | derived |

This matches the prototype (`total = available + pending`, "Pending Across Hivorr") and
`PAYMENT-WALLET-ESCROW-ARCHITECTURE.md` §2. An internal hold moves value from the wallet to the
escrow account, so it lowers `available` and raises `pending` by the same amount and leaves `total`
unchanged — the database test asserts exactly that.

`withdrawable` equals `available` **only until payout reservations exist**. `EP-02-053` adds the
reservation; this task does not invent a reservation table or a release policy. Release, refund and
dispute rules remain BD-D03.

## 4. Design decisions

| Decision | Reason |
|---|---|
| Views rather than service-side aggregation | The task asks for a read model, and a view is available to a future reporting role without duplicating the arithmetic. |
| `security_invoker` on both views | A view without it runs as its owner and would expose every wallet. This is the database rules §5.7 requirement. |
| Pending from held escrows only | A released or refunded escrow is no longer pending; its ledger net is expected to be zero, and the reconciliation job will catch a mismatch. |
| Zero read, not 404, for an empty wallet | A wallet exists from registration; the ledger history arrives with the first money movement. |
| No account parameter in the service | The caller cannot ask for another account's wallet; the session identity is the only source. |
| Keyset pagination on `(occurred_at, posting_id)` | Offset pagination skips or duplicates rows when new postings arrive between pages. |
| No audit on an owner's own wallet read | The rule audits privileged reads; a user reading their own statement is not one. Administrator reads remain `EP-02-056`. |
| No clamp on a negative balance | A negative figure is a defect to see, not to hide; `EP-02-035` owns the refusal that should prevent it. |
