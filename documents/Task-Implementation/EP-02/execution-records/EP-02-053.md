## 1. Implementation summary

**Durable request** (`finance.payout_requests`, migration `20261123000200`)
- one row per request with reference, account, destination, amount, currency, status, client
  idempotency key, requester and execution/provider fields;
- the status vocabulary is the approved `PAYOUT_STATES` contract;
- an insert policy allows only the owning account and current user, only in `REQUESTED`, with the
  execution fields empty;
- select is owner-scoped; execution adds an owner-scoped update path guarded by a trigger.

**Request and eligibility** (`server/src/modules/finance/payout-request.service.ts`)
- `request` refuses a caller below `tier_1` (`KYC_REQUIRED`), an invalid destination, non-NGN, an
  invalid amount and a short idempotency key before any database work;
- inside one transaction it refuses an unbound or unverified destination
  (`PAYOUT_ACCOUNT_REQUIRED`), applies the configured `payout` limit through
  `FinanceLimitService.assertWithin`, and refuses an amount above the derived available balance
  (`INSUFFICIENT_FUNDS`);
- a replay of the same key/destination/amount/currency returns the existing request; a changed amount
  or destination is `CONFLICT`;
- the insert records `REQUESTED` and audits `finance.payout_requested` with the last four only;
- `list` projects the request and last four only.

**Execution** (`server/src/modules/finance/payout-execution.service.ts`, migration `20261123000300`)
- `execute` transitions `REQUESTED -> RESERVED -> PROCESSING`, posting one `payout` journal entry:
  credit the user wallet and debit the platform `payout_payable` account;
- the reserve entry, the request status and the audit row share one transaction, through the new
  transaction-scoped `LedgerService.postEntryInTransaction`;
- `finance.ensure_ledger_account` provisions the wallet and payout-payable ledger accounts
  transactionally; the wallet owner must be the current account;
- after commit it calls the payout port with the request id as the provider idempotency key;
- `paid` marks the request `PAID`; `pending`/`processing` keeps `PROCESSING` with the provider
  reference; `failed` posts a `reversal` entry and marks `FAILED` in one transaction;
- a retryable provider error or a duplicate reference is ambiguous: the request stays `PROCESSING`
  with no reversal and must be reconciled by the status query;
- a non-retryable provider error reverses the reserve and marks `FAILED`;
- a repeat call for a `PROCESSING`/`PAID`/`FAILED` request returns the current state without a second
  provider call;
- the status trigger refuses a transition outside the approved path and refuses any change to the
  request's immutable financial fields.

**Wiring and exports**
- `PayoutRequestService` and `PayoutExecutionService` are registered in `AppModule`;
- `PAYOUT_PROVIDER` aliases `VFD_PAYOUTS`, so finance sees the provider-neutral port only;
- no live provider call was made.

## 3. Eligibility and execution rules

| Situation | Result |
|---|---|
| Tier below `tier_1` or missing | `KYC_REQUIRED` (403) |
| Invalid destination identifier | `VALIDATION_FAILED` (400) |
| Non-NGN currency | `VALIDATION_FAILED` (400) |
| Non-positive or malformed amount | `VALIDATION_FAILED` (400) |
| Idempotency key shorter than 8 characters | `VALIDATION_FAILED` (400) |
| Destination not owned or not found | `PAYOUT_ACCOUNT_REQUIRED` (403) |
| Destination not `verified` | `PAYOUT_ACCOUNT_REQUIRED` (403) |
| No configured `payout` limit or over limit | `LIMIT_EXCEEDED` (403) |
| Available balance below the amount | `INSUFFICIENT_FUNDS` (409) |
| Reused request key with a different amount/destination | `CONFLICT` (409) |
| Provider `paid` | `PAID`, provider reference stored |
| Provider `pending`/`processing` | stays `PROCESSING`, provider reference stored |
| Provider `failed` | reversal posted, `FAILED`, failure code stored |
| Provider retryable error or duplicate | stays `PROCESSING`, no reversal, reconcile via TSQ |
| Provider non-retryable error | reversal posted, `FAILED`, provider code stored |
| Repeat execution of a non-`REQUESTED`/`RESERVED` request | current state returned, no provider call |

## 4. Design decisions

| Decision | Reason |
|---|---|
| Reserve before the provider call | The wallet must be debited before an external movement; the payable account holds the obligation until settlement. |
| Reserve and status in one transaction | A crash cannot leave a posted reserve with a `REQUESTED` row. |
| Transaction-scoped ledger posting | The payout workflow must share the ledger, request and audit transaction; a second connection would break the invariant. |
| Reversal for a definitive failure | A provider failure must leave no net wallet movement; the reversal is append-only and auditable. |
| Ambiguous outcomes stay `PROCESSING` | A timeout or duplicate may mean the provider applied the transfer; reversing would risk paying twice. |
| Request id as provider idempotency key | A retry after a crash cannot create a second transfer. |
| `finance.ensure_ledger_account` is narrow | It creates only the current account's wallet or the platform payable account; no arbitrary ledger account. |
| Status trigger, not an update grant alone | RLS remains defence in depth; a direct writer cannot skip the state machine. |
| Automatic withdrawal has no maker-checker | The permission matrix requires KYC, a bound verified destination and limits for `wallet.withdraw`; dual control is for manual payouts. |
| Manual payout path deferred | It needs a distinct approver and a finance approval permission; wiring it through CP-020 is the next increment. |

## 9. Outstanding issues

- **Manual payout maker-checker is not implemented.** It needs a finance approval action, a distinct
  approver and a finance permission; CP-020 is the intended primitive.
- **A `payout` limit must be configured**; none is seeded. Until then every request fails closed with
  `LIMIT_EXCEEDED`.
- **`VFD_SOURCE_ACCOUNT` must be provisioned** for a live execution. Unset makes the adapter fail
  closed; the execution service then reverses and marks `FAILED`.
- **Provider reference linkage is not written to `finance.provider_references`.** The request stores the
  provider reference; reconciliation/audit coverage (`055`/`056`) must link it to the entry.
- **No DB integration run.** `pnpm test:db` and `db:snapshot` must run in CI.
- **No HTTP endpoint** exposes request or execution yet.
- A direct API-role writer could forge `PROCESSING -> PAID` within the allowed transition; `EP-02-054`
  adds the independent RLS eligibility gate. The client never holds a database credential.
