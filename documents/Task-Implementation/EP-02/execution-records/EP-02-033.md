## 1. Implementation summary

Escrow ledger accounts and metadata existed from `EP-02-030`. This task adds the reservation
lifecycle without deciding its policy.

**Shared transition table** (`ESCROW_TRANSITIONS` in `@hivorr/shared`)

| From | To | Enabled | Policy |
|---|---|---|---|
| `held` | `disputed` | **yes** | — (moves no money, asks for review) |
| `held` | `released` | no | BD-D03 |
| `held` | `refunded` | no | BD-D03 |
| `held` | `cancelled` | no | BD-D03 |
| `disputed` | `released` | no | BD-D03 |
| `disputed` | `refunded` | no | BD-D03 |

`evaluateEscrowTransition` returns `enabled`, `disabled` with the rule, or `invalid`. The UI can use
the same table to hide or disable an action without a second vocabulary.

**Database** (`20261118000400_finance_add_escrow_lifecycle.sql`)
- the API may insert an escrow ledger account (`kind = 'escrow'`, owner type `activity`) and an escrow
  reservation for its own payer account;
- only `state`, `updated_at` and `resolved_at` are update-granted; payer, ledger account, activity,
  reference and currency are immutable;
- RLS limits read and update to the payer;
- a trigger refuses every disabled or undefined transition with SQLSTATE `42501` or `23514`, so a
  caller that bypasses the service still cannot release or refund.

**Service** (`server/src/modules/finance/escrow.service.ts`)
- `openEscrow` creates the escrow ledger account and the held reservation in one transaction, then
  audits `finance.escrow_opened`;
- `transition` locks the reservation, evaluates the shared rule, refuses a disabled transition as a
  conflict, applies an enabled one, and audits `finance.escrow_state_changed` with before/after state;
- no money is posted here. The hold, release and refund postings belong to the money-flow tasks.

## 3. Design decisions

| Decision | Reason |
|---|---|
| Dispute is the only enabled transition | It changes metadata and asks for review; it moves no money and cannot end the reservation. |
| Release, refund and cancellation are disabled in the domain **and** the database | The policy is BD-D03; a service-only guard is not a control. |
| Transition table lives in `@hivorr/shared` | The portal needs the same disabled states; a second list would drift. |
| Column-level update grant | The payer, ledger account and amount-bearing fields must never change after opening. |
| Settle/resolve timestamps are not fabricated | `resolved_at` stays null until a terminal transition exists. |
| Opening creates the ledger account | A held balance must be represented in the ledger, not only in metadata. |
| Ledger account insert avoids `RETURNING` | Its select policy intentionally hides an escrow account until the reservation row exists; the id is taken from `platform.uuidv7()` and inserted explicitly, so the write does not depend on a read it cannot yet perform. |
| No fee or split column or calculation | Explicitly out of scope while fee rules are unapproved. |
