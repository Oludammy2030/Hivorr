## 1. Implementation summary

**Endpoints** (`server/src/api/verification-lane.controller.ts`, app audience)
- `GET /v1/verification/{lane}/status` — the caller's own lane state, reason code, whether an attempt
  is open and the last change time;
- `POST /v1/verification/{lane}/start` — opens a draft attempt; starting from a rejected or expired
  attempt is the resubmission path;
- `POST /v1/verification/{lane}/submit` — submits the draft attempt; requires an `Idempotency-Key`;
- `POST /v1/verification/{lane}/withdraw` — returns a submitted attempt to draft.

**Session and ownership**
- the account comes from the session; the lane comes from the path and is validated against the
  shared vocabulary;
- RLS filters every row a second time, so a forged account cannot read another lane's state.

**Rate limits** (`FixedWindowRateLimiter`, per user and action)
- start 10 / 15 min, submit 10 / 15 min, withdraw 20 / 15 min;
- refused calls are `RATE_LIMITED` (429) with a `retry-after` header;
- in-memory by design, matching the authentication limiter; a multi-instance deployment needs a
  shared store and the limiter is the seam.

**Idempotency**
- `submit` requires an `Idempotency-Key` header and hashes the logical request;
- `claimIdempotency` / `completeIdempotency` from the platform module are reused inside the same
  transaction, so a retry replays the stored lane status instead of submitting twice;
- a reused key with a different request is `CONFLICT` (409).

**Contract**
- four operations added; the document is regenerated (87 paths) and the typed client with it;
- the response is the shared `laneStatusSchema`, so the app and the API cannot drift.

**Capability**
- submission creates no capability. The shared vocabulary has no generic `verification.submit`
  (only `business.verification.submit`), so no capability is required or invented; authentication and
  row ownership are the gate. `EP-02-015` owns the reviewer authority.

## 3. Rules

| Situation | Result |
|---|---|
| No session cookie | `UNAUTHENTICATED` (401) |
| Unknown lane | `VALIDATION_FAILED` (400) |
| Read own lane with no case | `NOT_STARTED` with no active attempt |
| Start from `NOT_STARTED`/`REJECTED`/`EXPIRED` | draft attempt, 200 |
| Start on an approved lane or with an attempt open | `CONFLICT` (409) |
| Submit without a usable evidence row | `VALIDATION_FAILED` (400) |
| Submit without `Idempotency-Key` | `VALIDATION_FAILED` (400) |
| Submit retried with the same key and payload | replay of the stored status, 200 |
| Submit with the same key and a different payload | `CONFLICT` (409) |
| Withdraw while under review | `CONFLICT` (409) |
| More than the per-user limit | `RATE_LIMITED` (429) with `retry-after` |

## 4. Design decisions

| Decision | Reason |
|---|---|
| Logic in the service, HTTP thin | The controller maps session, rate and idempotency only; every rule stays testable without Nest. |
| Separate controller file from the control-portal one | `api/verification.controller.ts` already exists for reviewer actions; the subject surface must not merge with it. |
| Rate limits per user and action | A single bucket would let one action starve another. |
| Idempotency on submit only | Start/withdraw are guarded by the state machine; submit is the retry-sensitive command. |
| Replay stored status, not an empty 200 | A retry must see the same result the first call produced. |
| No capability gate | Inventing `verification.submit` would duplicate the approved vocabulary. |

## 9. Outstanding issues

- **No evidence upload.** `EP-02-012` needs an object-storage port, a bucket and a scanning decision.
  Until then `submit` always returns `VALIDATION_FAILED` for missing evidence.
- **Rate limits are per process.** A multi-instance deployment needs a shared counter; the limiter is
  the seam.
- **No page for the lanes.** The app still has no verification screen (`EP-02-060`); these endpoints
  are consumed by nothing yet.
- **Idempotency records expire after 24 hours.** A retry after that is treated as a new request, which
  the state machine then refuses as already submitted.
- **`submit` requires the key but `start`/`withdraw` do not.** They are guarded by state and resubmit
  is naturally repeatable; if a client needs strict replay there too, it is an additive change.
