## 1. Implementation summary

Created the `finance` schema that the later ledger tasks build on. The migration makes the approved
ledger rules structural rather than conventional:

- `finance.ledger_accounts` with the seven approved account kinds and a constraint tying each kind to
  its owner type (`account` for wallets, `activity` for escrow, `platform` for clearing, fee,
  payable and adjustment accounts);
- `finance.journal_entries` and `finance.postings`, both append-only and currency-dimensioned;
- a deferred constraint trigger that refuses to commit an entry with fewer than two postings or a
  non-zero sum per entry;
- a before-insert trigger that refuses a posting whose currency differs from its entry or its ledger
  account, and refuses an inactive account;
- update, delete and truncate triggers on the ledger tables, so append-only does not rely on grants;
- `finance.provider_references` with a unique `(provider, provider_reference)` pair and a required
  entry link once posted;
- `finance.escrow_accounts` metadata with the five approved states, no stored amount, and a trigger
  that binds the escrow row to an `escrow` ledger account owned by the same activity record;
- `finance.payout_accounts` that store only ciphertext, key version, last four digits, an HMAC
  fingerprint and the normalised account name;
- `finance.limits` that target either a tier or an account, never both, with effective dates;
- `finance.reconciliation_runs` and `finance.reconciliation_items` with generated differences.

No mutable balance column exists. Money is `numeric(20, 4)` with an explicit currency everywhere.
No fee, split, refund, release or marketplace rule was invented.

## 3. Deliberate design decisions

| Decision | Reason |
|---|---|
| No insert, update or delete grant to any application role | The posting engine (`EP-02-031`) and its callers own the write path. A schema without a write path cannot be used to bypass the engine. |
| Owner-scoped RLS reads only; no blanket administrator policy | Database rules §12.8 require scoped, logged, non-bulk admin reads. A blanket `payment.review` policy would be unaudited. Audited read functions arrive with `EP-02-056`. |
| Reconciliation tables have no read grant at all | No consumer exists before `EP-02-055`; the tables fail closed. |
| Balance check is deferred | An entry and its postings are written in one transaction; a per-statement check would reject the first posting of every valid entry. |
| Escrow rows carry no amount | The held amount is derived from postings; storing it would create a second, mutable source of truth. |
| `limits.tier` accepts `tier_N` without seeding a ladder | The KYC ladder (#6) is still open; the schema must not invent it. |
| No default currency and no currency row | The currency model (#9) is still open; only the dimension exists. |

## 4. Field-level encryption specification for bank details

`finance.payout_accounts` never holds a plaintext account number.

| Element | Specification |
|---|---|
| Ciphertext | AES-256-GCM with a fresh 96-bit nonce per write; ciphertext and nonce stored together in `account_number_ciphertext`; authentication tag required on decrypt |
| Key management | Key supplied at runtime from the managed secret store (Doppler); never in the repository or database |
| Key rotation | `encryption_key_id` records the version used; a rotation re-encrypts rows in a controlled job and keeps the old key until the job completes |
| Lookup and uniqueness | `account_number_fingerprint` is HMAC-SHA256 over the normalised account number with a key separate from the encryption key; the unique index uses it |
| Display | Only `account_number_last4` may appear in a projection, statement, audit summary or log |
| Decryption boundary | API process only, inside the payout/name-enquiry flow; never in a worker log, error payload or analytics event |
| Failure behaviour | A decrypt failure is a typed error and a `500` without the ciphertext or key identifier in the response |
