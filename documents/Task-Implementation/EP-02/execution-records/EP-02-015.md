## 1. Implementation summary

**Submission opens the review**
- `admin.open_verification_review(actor, account, submission, title)` is security-definer because a
  subject has no case-management permission;
- it re-checks that the submission belongs to the account and is `SUBMITTED`, then creates one
  `verification_review` case (`subject_type = verification_submission`, `subject_id = submission id`),
  one pending `admin.verification_reviews` row with the lane, and a `verification_submitted` case
  event;
- `VerificationLaneService.submit` calls it after the lane moves to `SUBMITTED`, in the same
  transaction.

**The queue follows the subject**
- `admin.list_verification_queue` now counts a lane submission's evidence from
  `profile.verification_evidence`; a control-portal case still counts `admin.case_evidence`;
- lane, subject and evidence count therefore appear in the existing queue without a second view.

**The decision is atomic and immutable**
- `admin.record_verification_decision` keeps its signature and permission check, and now:
  - resolves the lane submission through the case subject and requires it to be `UNDER_REVIEW`;
  - moves the submission and its lane case to `APPROVED` or `REJECTED` in the same transaction;
  - maps `request_information` to `REJECTED` with reason code `information_required`, because the
    shared state set has no information-requested state — the lane then reopens;
  - inserts one `profile.verification_decisions` row with the actor, the reason, the prior and next
    state, and the evidence ids that were on the attempt;
  - on the `kyc` lane only, an approval calls `identity.set_kyc_tier` with the tier the subject asked
    for, which also clears any KYC-upgrade hold and audits the tier change;
  - keeps the existing case status, outcome, closure reason and timeline event.
- a subject cannot approve: the function still requires `admin.verification.review`, and no
  subject-side path calls it. There is no scheduled approval job.

**Requested tier**
- `profile.verification_submissions.requested_kyc_tier` records what the subject asked for;
- the `kyc` lane requires it at start and every other lane refuses it (API contract updated);
- a rejection leaves the tier untouched.

**Decision record additions**
- `from_state`, `to_state`, `evidence_ids` and `admin_case_id`; `case_id` remains the lane case, and
  the control case is a separate reference.

## 3. Rules

| Situation | Result |
|---|---|
| Submit a lane attempt | case + queue row created in the same transaction |
| Subject calls the decision function | `42501` |
| Approve an attempt not `UNDER_REVIEW` | `23514` |
| Approve | submission and lane `APPROVED`; decision row with `UNDER_REVIEW → APPROVED` |
| Reject | submission and lane `REJECTED`; decision row; lane reopens |
| Request information | `REJECTED` with `information_required`; lane reopens |
| Approve the `kyc` lane | account tier becomes the requested tier |
| Approve a non-`kyc` lane | tier untouched |
| Re-submit after rejection | new attempt, new case, new queue row |

## 4. Design decisions

| Decision | Reason |
|---|---|
| Security-definer open function | A subject legitimately opens a review but must never hold case-management permission. |
| Subject link on the case, not a new column | `admin.cases` already has typed subject links; a parallel column would duplicate the spine. |
| Evidence count follows the subject type | Lane evidence lives in `profile`; a second copy in `admin.case_evidence` would drift. |
| Request-information maps to rejection | The shared vocabulary has no information state; inventing one would change an approved contract. |
| Tier set only on kyc approval | Other lanes have no tier effect, and a rejection must not move money eligibility. |
| Decision and lane in one function | The task requires them to commit together; a service-side sequence could half-apply. |

## 9. Outstanding issues

- **The control-portal page is not reworked.** The existing verification screen lists the queue and
  records a decision; it now shows lane submissions because the queue does. A richer review view
  (evidence previews) waits for `EP-02-012`'s signed read.
- **Information requests are rejections with a reason code.** A dedicated state would need a shared
  vocabulary change.
- **The subject is not notified.** No email or in-app notification is emitted on a decision; that is
  outside this task.
- **A decided case cannot be reopened.** `EP-02-016` owns overrides with dual control.
