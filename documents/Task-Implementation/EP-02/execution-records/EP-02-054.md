> **Why the service alone was not enough.** `PayoutRequestService` checks tier, destination,
> ownership, limits, balance and the financial hold inside the transaction. A caller that reaches
> `finance.payout_requests` directly — a future endpoint, a migration, a mistaken grant — would skip
> all of it. RLS is the second line and it fails closed.

---

## 1. Implementation summary

**`finance.payout_requests` insert policy** (`20261127000900`)
- keeps every existing guard: own account, own user, `REQUESTED`, no approval, provider or entry set;
- adds a destination check: the referenced payout account must belong to the same account and be
  `verified`;
- adds an account check: `kyc_tier` must be `tier_1`–`tier_3` and `financial_hold_reason` must be
  null.

**`finance.payout_accounts` insert policy**
- binding now also requires `tier_1` or above and no financial hold, so a `tier_0` account cannot
  create the destination that a payout would later use.

**Identity source**
- both policies read `platform.current_account_id()` and `platform.current_user_id()` only. No
  Supabase auth helper and no client-supplied account id appear in any policy; a repository-wide scan
  asserts it.

**Service layer**
- unchanged and still authoritative: it applies the same rules plus amount limits, derived balance
  and idempotency, which RLS does not attempt to compute.

## 4. Design decisions

| Decision | Reason |
|---|---|
| Gate on insert, not update | The request is created eligible or not at all; execution transitions must remain possible under the same row. |
| Reuse the identity context | The project forbids Supabase auth helpers; the test asserts no policy references one. |
| Keep balance and limits in the service | RLS cannot compute a derived balance without a second policy on the ledger, which would slow every insert and duplicate the limit engine. Recorded rather than implied. |
| Not re-check on execution | Eligibility was proven at creation and the row is locked; a hold set later is enforced by the service before it reserves. |
| Bind gate on `payout_accounts` too | Otherwise a `tier_0` account could prepare the destination and wait. |

## 9. Outstanding issues

- **Limits and balance are not enforced in RLS.** A direct insert above the daily cap or the available
  balance would pass the policy. Enforcing it needs a derived-balance read inside the policy; the
  service remains the only place that computes it. The task's DoD does not require it, but it is the
  remaining gap in a full bypass story.
- **Execution is not re-gated by RLS.** A row created eligible and later hit by a hold is stopped by
  the service before it reserves; RLS on the update path would need the same derived reads.
- **A refused write is not audited.** The error is visible to the caller; there is no audit event for
  an RLS denial. That is consistent with other policies but worth knowing.
