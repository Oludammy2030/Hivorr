## 1. Implementation summary

**Schema** (`20261123000400`, `20261123000600`)
- `identity.accounts.kyc_tier` with `tier_0` default and a check for the CBN values
  `tier_0`–`tier_3`;
- `kyc_tier_updated_at`;
- `identity.set_kyc_tier(actor, account, tier, reason)`, a security-definer function that requires
  `admin.verification.review`, validates the tier and reason, and returns the updated row;
- no evidence rule or verification-vendor behaviour is invented.

**Tier-based limits** (`20261123000700`, `20261123000800`)
- `tier_1`/`tier_2`/`tier_3` are CBN Levels 1/2/3 with daily withdrawal caps of
  ₦30,000/₦100,000/₦1,000,000;
- the rows live in `finance.limits` as `limit_type='withdrawal'`, `period='daily'`,
  `currency='NGN'`; the earlier `tier_1` ₦100,000 row is closed by `effective_to`;
- the self-service withdrawal uses the `withdrawal` limit type, so the cap is applied by the existing
  effective-dated limit engine;
- **deposits** use the CBN single-deposit caps ₦20,000/₦50,000/unlimited for
  `tier_1`/`tier_2`/`tier_3`; an over-cap deposit sets a `kyc_upgrade_required` hold,
  refuses the credit, and blocks every fund transaction until a verifier upgrades the tier;
- `tier_0` is denied before the limit check; a later decision changes a cap with a new effective-dated
  row, not a code change.

**Capability input**
- `buildAccessContext` and `loadAccessContext` now carry `kycTier`, read from the account;
- `getSession` returns `kycTier` and composes capabilities with it, so `wallet.withdraw` can become
  available when the account is `tier_1`;
- the current-session contract includes `kycTier`.

**Assignment**
- `IdentityService.setKycTier` validates the tier and reason, calls the database function and audits
  `identity.kyc_tier_changed` with the previous and new tier;
- `POST /v1/control/accounts/{id}/kyc-tier` exposes the verifier action; the database re-checks
  `admin.verification.review`;
- the action is independent of activity lanes.

**Self-service withdrawal**
- `POST /v1/wallet/withdrawals` and `GET /v1/wallet/payouts` are now exposed (`EP-02-053`);
- the controller passes the session tier to the request/execution services; no tier is inferred from
  the request body.

## 8. Outstanding issues

- The CBN tier ladder is recorded as `tier_1`–`tier_3` = Levels 1–3; the evidence required to reach
  each tier and the verification-to-tier wiring remain open.
- The seeded daily withdrawal caps are ₦30,000/₦100,000/₦1,000,000 and the single-deposit caps are
  ₦20,000/₦50,000/unlimited. Changing one is a new effective-dated `finance.limits` row.
- The deposit gate (`DepositEligibilityService`) must be called by `EP-02-052` when deposit posting
  lands; until then no deposit path consumes it.
- An over-cap deposit cannot be stopped at the bank. Hivorr refuses the wallet credit and sets the
  hold; the unmatched collection credit must be handled by reconciliation/manual review.
- Verification decisions (`EP-02-015`) must set the tier automatically; today a verifier assigns it.
- No tier history table; the audit log is the history.
- DB integration and RLS tests must run in CI.
- Configuration-driven tier definitions are not implemented; only the two approved values exist.
