# Task Implementation Plan — EP-02-01: Two-Tier Taxonomy Seed Data & Registry Population

---

## 1. Task Objective

Create a Supabase SQL migration that seeds the existing `industries` and `professions` tables with an initial registry of industries and their associated professions for the Nigerian market. Define SEO-stable slugs, deterministic sort ordering, and active status for all seeded records. Include a pgTAP verification test to confirm seed data integrity.

---

## 2. Business Problem Being Solved

The two-tier taxonomy (`industries` → `professions`) is the universal classification backbone of the Hivorr platform. The EP-01 schema created the empty tables with full constraints, RLS, and indexes — but zero data exists. Without seed data:

- Entities cannot select a profession during onboarding (EP-02-18)
- Trade verification cannot be tested end-to-end (EP-02-11)
- The client-side taxonomy engine (EP-02-07) has nothing to browse
- Entity profession binding (`entity_profession_bind` RPC) cannot be validated with real data
- All downstream EP-02 tasks that depend on taxonomy data are blocked

This task unblocks the entire EP-02 pipeline starting from Stage 1.

## 5. Recommended Technical Approach

### 5.1 Single Idempotent SQL Migration

Create one new migration file following the established naming convention:

```
supabase/migrations/<YYYYMMDD><HHMMSS>_taxonomy_seed_data.sql
```

The migration will use `INSERT INTO ... ON CONFLICT (slug) DO NOTHING` to ensure idempotency — safe to re-run without duplicating records or failing on existing data.

### 5.2 Two-Phase Insert Pattern

1. **Phase 1 — Industries:** Insert all 8 industries first (no FK dependencies)
2. **Phase 2 — Professions:** Insert professions referencing industry IDs via subselects on `industries.slug` (not hardcoded UUIDs) to maintain referential integrity without depending on auto-generated IDs

### 5.3 Slug Strategy

- Industry slugs: single-word or short kebab-case (`legal`, `technology`, `healthcare`, `construction`, `financial-services`, `creative`, `education`, `logistics`)
- Profession slugs: globally unique kebab-case, prefixed with domain context where ambiguity exists (`corporate-lawyer`, `criminal-lawyer`, `software-engineer`, `electrician`, `pharmacist`)
- All slugs must pass the existing CHECK constraint: `lower(slug) AND slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$' AND char_length(slug) <= 140`

### 5.4 Sort Ordering

- Industries: `sort_order` assigned in increments of 10 (10, 20, 30...) to allow future insertions without renumbering
- Professions: `sort_order` assigned in increments of 10 within each industry scope

### 5.5 No Hardcoded UUIDs

Industry IDs will be auto-generated by `gen_random_uuid()`. Profession inserts will resolve `industry_id` via `SELECT id FROM industries WHERE slug = '...'` subselects, ensuring FK validity regardless of UUID generation.

## 8. Database Considerations

### 8.1 Existing Schema (No Modifications)

This task inserts data into the existing tables defined in `20260821090001_entity_taxonomy_tables.sql`. No DDL changes (CREATE, ALTER, DROP) are performed.

### 8.2 Constraint Compliance

All seed data must satisfy:
- `industries_slug_format`: lowercase, kebab-case regex, ≤140 chars
- `industries_name_length`: trimmed name between 1–255 chars
- `professions_slug_format`: same as industries
- `professions_name_length`: same as industries
- `professions.industry_id` FK: must reference existing `industries.id` (ON DELETE RESTRICT)
- `industries_slug_key` / `professions_slug_key`: global uniqueness

### 8.3 RLS Bypass for Seeding

The migration runs as the `postgres` superuser (migration context), bypassing RLS. The existing RLS policies already grant `service_role` INSERT access, and migrations execute with elevated privileges. No RLS policy changes are needed.

### 8.4 Idempotency Strategy

Use `INSERT INTO ... ON CONFLICT (slug) DO NOTHING` on both tables. This ensures:
- Re-running the migration does not fail or duplicate data
- Existing manually-inserted records (e.g., from testing) are preserved
- Safe for multi-environment deployment (dev, staging, prod)

### 8.5 Transaction Safety

The entire migration will be wrapped in an implicit transaction (Supabase migrations run transactionally by default). If any insert fails unexpectedly, the entire migration rolls back.

### 8.6 `created_by` Column

Seed data inserts will explicitly set `created_by` to `NULL` (or omit it, letting the default `auth.uid()` resolve to `NULL` in migration context since there is no authenticated session). This correctly indicates system-seeded data rather than user-created data.

### 14.2 Test Execution

The test follows the existing pgTAP pattern: `begin; set search_path; select plan(N); ... select * from finish(); rollback;`

### 14.3 Manual Verification

Post-migration, verify via:
```sql

FROM industries i
LEFT JOIN professions p ON p.industry_id = i.id

ORDER BY i.sort_order;
```
