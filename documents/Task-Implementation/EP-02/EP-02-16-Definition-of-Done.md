## 1.1 Implementation Mapping & Deviations

EP-02-16 was implemented in this repository under coverage-equivalent names/structures rather than
every file name written in this DoD. Boxes are ticked when the **intent** is satisfied by built,
tested artifacts; plan-only artifacts that were not built are annotated `N-A` (deferred) and left
unchecked. Key mappings and deviations:

- **Schema names:** this repo's frozen migration (`20260829100004_financial_integrity_schema.sql`)
  defines `financial_payout_accounts`, `financial_payouts`, `financial_deposits`. Payout accounts
  carry `status` (`pending|active|deactivated`) + `is_verified`, and deposits carry
  `name_match_status` (`unverified|pending|matched|mismatched`) — not the `verification_status`
  4-state columns referenced in this DoD.
- **Enum vocab:** `models/payout_account_status.dart` (`PayoutAccountStatus`, `displayLabel`) ~
  FV-01 `AccountVerificationStatus`; `models/deposit_name_match_status.dart`
  (`DepositNameMatchStatus`, labels Unverified/Pending/Verified/Failed) ~ FV-02
  `DepositVerificationStatus`. Both unit-tested (`values.length`, `fromPersisted` default mapping).
- **Data layer:** `lib/data/entities/` (`PayoutAccount`, `Deposit`, `WithdrawalResult`) +
  `lib/data/models/` (`PayoutBindDto`, `WithdrawalDto`, `DepositDto`) + `lib/data/mappers/`
  (`FinancialPayoutMapper`, `FinancialDepositMapper`) replace the plan's
  `lib/data/entities/financial/{model,entity,mapper}` split. No `copyWith`; the RPC payloads are
  parsed by DTOs.
- **Remote data sources:** `lib/data/datasources/remote/financial_payout_remote_data_source.dart` +
  `financial_deposit_remote_data_source.dart` (abstract) and their `Supabase...` impls extending
  `BaseApiService` replace the plan's `lib/core/api/datasources/*`. Envelope unwrapping reuses
  `financial_envelope_parser.dart`; exceptions normalize through `data_exception_mapper.dart`.
  The deposit source is read-only (`listDeposits` via RLS-scoped REST select); the service-role
  write RPCs are never surfaced as client methods.
- **UI:** `lib/systems/finance/widgets/*` (view, bind form, withdraw form, card, limit display,
  deposit panel, name-match indicator, history badge) replace the plan's
  `lib/features/finance/screens/*`; sections are embedded in `financial_profile_screen.dart` (the
  repo's `/finance` screen). **No transaction-history view was built** — payout cards + deposit
  list + history badge live on the profile screen.
- **Providers:** `financial_payout_provider.dart` / `financial_deposit_provider.dart` are
  load/bind/withdraw `ChangeNotifier`s with `_disposed` guards and in-memory state; they have **no**
  polling `Timer` and **no** `WidgetsBindingObserver` lifecycle gate, so `pausePolling`/
  `resumePolling` boxes are N-A.
- **Not built -> N-A** throughout: per-currency account tabs (Accounts/Withdraw tab selector used),
  NIBSS bank selector + name-enquiry autofill, `DepositNameMatchService`/`NameEnquiryService` seam,
  service-role deposit RPC client seams + proxy feature flags (`...ViaProxyEnabled`),
  cross-currency USD/GBP/EUR->NGN conversion preview with rate/timestamp, 48h cooling-off countdown
  UI, per-transaction/daily/monthly limit breakdown, transaction-history view, provider
  polling/lifecycle, and the EP-02-16 fake-E2E integration test file. All N-A facets remain
  server-authoritative or staged to EP-02-18.

## 2. Functional Verification

This task delivers the **bound payout account registry** with KYC-tiered limits and the **deposit name verification system** satisfying `AGENT.md` Rule 3. The payout account bind and withdrawal RPCs are `authenticated` (client-callable); the deposit record/verify/name-check RPCs are `service_role` only (never callable from client code — proxy deferred to EP-02-18). Functional verification confirms the enum vocabulary, data layer, two-tier data sources, repositories, services, providers, UI screens/widgets, and routing behave correctly and never bypass server invariants or the `service_role` boundary.
