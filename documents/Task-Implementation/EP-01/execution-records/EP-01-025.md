## 1. Implementation summary

FORCE RLS already existed on the identity tables. This execution completed the pattern:

| Area | Result |
|---|---|
| Private helpers | `private.current_account_id`, `current_user_id`, `set_identity_context`; revoked from PUBLIC |
| Platform wrappers | `platform.current_*` and `set_identity_context` are security definer and delegate |
| FORCE RLS | Added to `profile.profiles` and `profile.activity_activations` |
| Profile policies | Recreated with explicit roles: select for API/readonly; insert/update for API |
| Definer owner | Seven narrow read policies for `hivorr_migrator`/`postgres` on the tables the current security-definer functions query |
| No-context | Users, profiles, activations and sessions return zero rows |
| Cross-account | Profile writes and session reads are filtered |
| Pre-auth | Valid lookup returns one row; unknown and closed accounts return none |
| `auth.uid()` | Absent |

**Scope note.** `platform.audit_log`, `outbox`, `idempotency_keys`, `feature_flags` and
`reference_counters` are service-internal and have no account column. They keep table grants and
append-only controls, not RLS. Recorded as `F-32`.

## 3. Architectural and technical decisions

| Decision | Reason | Reversible |
|---|---|---|
| Helpers live in `private`; `platform` wraps them | The plan asks for private helpers; existing policies and service calls keep their names | Yes |
| Wrappers are security definer | Callers should not need EXECUTE on the private functions | Yes |
| FORCE RLS on profile tables | Consistency with identity; the owner cannot silently bypass | Yes |
| Profile policies name roles explicitly | Least privilege; PUBLIC is not a policy subject by default | Yes |
| Owner-read policies for 7 tables | FORCE applies to the owner; narrow definer functions need read access | Yes |
| No RLS on platform system tables | They have no account column and the worker reads across accounts | Yes, by a later ruling |
