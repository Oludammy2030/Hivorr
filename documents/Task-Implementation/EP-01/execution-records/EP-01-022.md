## 1. Implementation summary

Migration `003` created the five roles and their base grants, but PostgreSQL still gives PUBLIC
EXECUTE on every new function and there were no default-privilege rules. This execution added a
forward-only migration and strengthened the tests.

| Area | Result |
|---|---|
| Roles | Five `nologin` roles; no superuser, `bypassrls`, `createdb` or `createrole` |
| API DDL | No CREATE, ALTER or TRUNCATE; asserted in the fresh-database suite |
| Defaults | Tables, sequences and functions revoked from PUBLIC; future functions start closed |
| Existing functions | PUBLIC execute revoked across all ten module schemas; explicit grants preserved |
| Schemas | `public` is not writable by application roles; `private` stays closed |
| Isolation | Worker cannot read `identity.users`; readonly cannot insert audit |
| Migration lint | `20261109000100_platform_alter_default_privileges.sql` is the first strict-named file |

**Applied migration `003` was not edited.** The change is a new forward-only migration, as §9.3
requires.

## 3. Architectural and technical decisions

| Decision | Reason | Reversible |
|---|---|---|
| Add a new migration instead of editing `003` | Applied migrations are immutable; a checksum change is refused by the runner | Yes, by a later migration |
| Revoke PUBLIC execute on all module schemas | Closes functions that individual migrations missed, including trigger functions | Yes |
| Set default privileges for the applying role | Defaults are per-creator; the deployment must keep one migration role | Yes |
| Keep explicit grants | API/worker helpers already have them; the fresh-database suite proves the paths still work | Yes |
| Close `public` and `private` | No application role should create in `public` or read `private` | Yes |
| Set no default table grants | The intended posture is default-closed; each owning migration grants explicitly | Yes |
