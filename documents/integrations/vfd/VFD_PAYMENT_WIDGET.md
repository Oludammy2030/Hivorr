# VFD Payment Widget

> **Source:** [Payment Widget](https://vbaas-docs.vfdtech.ng/docs/wallets-api/Products/payment-widget)
> **Retrieved:** 6 November 2026. **Documentation only.**
>
> The vendor describes the widget as enabling "instant payment collection using bank transfer, QR
> code, card and USSD payment methods". It is a browser SDK, not a REST API.

---

## 1. Authorization and environments

**Confirmed:** the widget is initialized with a **wallet access token** (`token`), the same token
described in [VFD_AUTHENTICATION.md](VFD_AUTHENTICATION.md). The page links to the Authorization page
for token generation.

| Environment | SDK script URL |
| --- | --- |
| Development / Test | `https://payment-widget-dev.vfdtech.ng/sdk/v-payment-widget.js` |
| Production / Live | `https://payment-widget.vfdtech.ng/sdk/v-payment-widget.js` |

**Confirmed:** use the development URL while testing and replace it with the production URL at go-live.
Do not load both URLs on the same page.

> **Observation:** the widget does not call a VFD REST endpoint directly from Hivorr's backend. The
> browser loads VFD-hosted JavaScript and the wallet token is placed in client-side code. See §8.

---

## 2. Integration approaches

The page documents three equivalent launch methods:

1. A plain HTML file with a `<script>` tag.
2. Any JavaScript framework, with the SDK script added to the main HTML file.
3. A React component, either through the global `window.VPaymentWidget` or the npm package
   `@tpsl/payment-widget`.

### 2.1 HTML

Add the SDK script to the page, then construct the widget and call `pay()`:

```html
<script src="https://payment-widget-dev.vfdtech.ng/sdk/v-payment-widget.js"></script>
```

```js
const widget = new VPaymentWidget({
  token: "XXXXXX",
  merchantId: 1,
  environment: "development",
  email: "user@email.com",
  logo: "",
  customizeMerchantName: "Example Store",
  successRedirectUrl: "",
  reference: "rosapay-0191",
  onSuccess: callBackFunc,
});

await widget.pay({
  amount: 1000,
});
```

### 2.2 Framework-agnostic JavaScript

The page instructs the developer to add the same script tag to `index.html` or the main HTML file,
then initialize `VPaymentWidget` in a JavaScript file with the same options.

### 2.3 React via global

```jsx
function App() {
  async function pay() {
    const widget = new window.VPaymentWidget({
      token: "XXXXXX",
      merchantId: 1,
      environment: "development",
      email: "user@email.com",
      reference: "rosapay-0191",
      logo: "",
      customizeMerchantName: "Example Store",
      successRedirectUrl: "",
      onSuccess: success,
    });
    await widget.pay({
      amount: 5000,
    });
  }

  function success(data) {
    console.log(data);
  }

  return (
    <div className="App">
      <button onClick={pay}>Pay</button>
    </div>
  );
}
```

### 2.4 React via npm package

```bash
npm install @tpsl/payment-widget
```

```jsx
import VPaymentWidget from "@tpsl/payment-widget";

function App() {
  const pay = async () => {
    const widget = new VPaymentWidget({
      token: "<VFD wallet access token>",
      merchantId: 1,
      environment: "development",
      email: "customer@example.com",
      logo: "https://example.com/logo.png", // optional
      customizeMerchantName: "Example Store", // optional
      reference: "order-123", // optional; generate a unique value for your order
      successRedirectUrl: "https://example.com/payment-complete", // optional
      onSuccess: ({ method, reference }) => {
        console.log("Payment completed", method, reference);
      },
    });
    await widget.pay({ amount: 1000 });
  };

  return (
    <div className="App">
      <button onClick={pay}>Pay</button>
    </div>
  );
}
```

> **Observation:** the npm package is published under the `@tpsl` scope, consistent with the
> "Product Studio Limited" publisher name on the documentation site. The page does not state the
> package version, peer dependencies, bundle size, or licence.

## 3. Initialization fields

| Field | Description | Required |
| --- | --- | --- |
| `token` | Wallet access token. The page links to the Authorization page for generation. | Mandatory |
| `merchantId` | "Customer's id on your system". | Mandatory |
| `environment` | `development` while integrating; `production` at go-live. The page suggests an environment variable. | Mandatory |
| `logo` | URL of the company logo. | Optional |
| `email` | Email of the customer making payment. | Mandatory |
| `customizeMerchantName` | Merchant name to display in the widget. | Optional |
| `reference` | Unique reference generated by the merchant to identify the transaction. | Optional |
| `onSuccess` | Callback invoked with `{ method, reference }` when payment succeeds. `method` is the payment method; `reference` is the unique transaction reference generated by VFD. | Optional |
| `successRedirectUrl` | Page the customer is redirected to after completing payment. | Optional |

**Confirmed:** `pay()` takes an `amount`. The examples pass a number (`1000`, `5000`) and, in the HTML
form example, a string read from an input.

> **Observation:** `merchantId` is described as the **customer's** ID on the merchant's system, not as
> the merchant profile ID used by the Payment Link API. The two APIs both use a field called
> `merchantId` with different descriptions. Do not assume the values are interchangeable.

## 4. Payment methods

**Confirmed:** the widget supports:

- bank transfer;
- QR code;
- card;
- USSD.

**Confirmed notification routing:**

| Payment method | Notification received |
| --- | --- |
| Pay with Transfer, Pay with USSD, Pay with QR Code | The **Inward Credit Notification** payload documented on the Wallets page. |
| Pay with debit card | The **Card Payment notification** payload documented on the Card Payment page. |

Both payloads are reproduced in [VFD_WEBHOOKS.md](VFD_WEBHOOKS.md).

> **Observation:** the widget page does not state whether the widget collects the payer's card details
> itself (keeping Hivorr out of card-data scope) or returns them to the host page. It also does not
> state which card networks are supported.

---

## 5. Success handling

**Confirmed:** `onSuccess` receives an object with:

| Field | Description |
| --- | --- |
| `method` | The payment method used. |
| `reference` | The unique transaction reference generated by VFD. |

**Not documented:**

- the exact set of `method` values;
- whether `onSuccess` fires before or after settlement;
- a failure, cancellation, or error callback;
- whether the widget closes automatically after success;
- how to reconcile `reference` with the merchant-supplied `reference` (the callback's `reference` is
  described as VFD-generated, while the initialization `reference` is merchant-generated);
- whether `successRedirectUrl` is called with query parameters.

> **Open question:** because the callback reference is VFD-generated, the merchant's own reference may
> not be returned. Server-side reconciliation should rely on the webhook and a status check, not on
> `onSuccess` alone. The page does not document a widget-specific verification endpoint.

## 6. Amount handling

**Confirmed:** `widget.pay({ amount })` accepts the amount to collect.

**Not documented:**

- currency (naira is implied by the rest of the documentation but not stated here);
- minimum and maximum amount;
- whether decimals are accepted;
- whether the payer can edit the amount;
- fee handling and who bears the fee;
- whether partial payments are allowed.

## 8. Security review notes

**Confirmed by the source:** the wallet access token is supplied to a browser-side constructor.

**Observation — high risk:** any value passed to browser JavaScript is visible to the payer and to any
script on the page. A wallet access token can authorize wallet operations beyond the widget. This is
material because:

- the token endpoint allows `validityTime: "-1"` (non-expiring) — see
  [VFD_AUTHENTICATION.md](VFD_AUTHENTICATION.md);
- the token is not described as scoped, short-lived, or widget-specific;
- the page does not document origin restrictions, domain allow-listing, or token binding.

**Open questions for the vendor:**

1. Is there a widget-specific, short-lived, origin-restricted token instead of a full wallet token?
2. Can the token be scoped to collection only?
3. What prevents a copied token from being used against the REST API?
4. Is the SDK served with Subresource Integrity (SRI) hashes?
5. What data does the SDK store in the browser (local storage, cookies, session storage)?
6. Does the widget handle card data directly, and if so, is the merchant in PCI scope?

**Recommendation for any future Hivorr use:** do not place a long-lived wallet token in client code.
Obtain a scoped/short-lived token or use a server-initiated collection flow instead. This is a security
review item, not an integration decision.
