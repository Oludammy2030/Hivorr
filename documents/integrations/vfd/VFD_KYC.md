## 2. AML verification

**Path:** `/aml/verification`
**Method:** `POST`
**Description:** performs anti-money-laundering checks, mainly sanctions screening and politically
exposed person (PEP) screening.

### 2.1 Request

```json
{
  "firstname": "Akintunde",
  "lastname": "Rotimi",
  "email": "akinrotimi@gmail.com",
  "phoneNo": "07055666667",
  "clientId": "7859",
  "dateOfBirth": "17-Apr-1981"
}
```

| Field | Description | Required |
| --- | --- | --- |
| `firstname` | Customer's first name. | Mandatory |
| `lastname` | Customer's last name. | Mandatory |
| `email` | Customer's email. | Mandatory |
| `phoneNo` | Customer's phone number. | Mandatory |
| `clientId` | Customer's client ID — "a unique reference generated by you". | Mandatory |
| `dateOfBirth` | Date of birth. Must use the format `17-Apr-1981`. | Mandatory |

**Observation:** `firstname` is one word here, unlike `firstName` in the driver-licence and NIN
responses. Field casing is not consistent across the KYC family.

**Observation:** the date format is different from the other KYC endpoints: AML uses
`DD-Mon-YYYY`, Driver License uses `YYYY-MM-DD`.

### 2.2 Response

```json
{
  "responseCode": null,
  "hasError": null,
  "message": null,
  "data": {
    "description": "Data added successfully",
    "status": "200"
  }
}
```

**Observation:** this is the only KYC response that does not use the usual `status` / `message` /
`data` envelope. `responseCode`, `hasError`, and `message` are all `null`, while `data.status` is
`"200"` — a string, not the numeric HTTP status and not the `"00"` success code used elsewhere.

**Not documented:**

- the match/no-match result;
- sanctions or PEP hit details;
- a risk score or confidence value;
- a screening reference or case ID;
- error responses;
- whether screening is synchronous or asynchronous;
- how to retrieve the result later.

**Open question:** "Data added successfully" suggests the request registers data for later screening
rather than returning a screening result. The page provides no way to obtain that result. Ask PSL how
AML outcomes are delivered.

## 3. Driver licence verification

**Path:** `/driver-license/verification`
**Method:** `POST`
**Description:** confirms whether a driver's licence is valid and returns the information on it.

### 3.1 Request

```json
{
  "firstName": "Andrew",
  "lastName": "Doe",
  "gender": "male",
  "dob": "1960-10-31",
  "idNumber": "FFF39140AA98"
}
```

| Field | Description | Required |
| --- | --- | --- |
| `firstName` | Customer's first name. | Mandatory |
| `lastName` | Customer's last name. | Mandatory |
| `gender` | Customer's gender. | Mandatory |
| `dob` | Date of birth. Must use `YYYY-MM-DD`. | Mandatory |
| `idNumber` | Driver licence number. | Mandatory |

**Confirmed:** the test environment uses the same payload as the sample above.

**Observation:** the `note` repeats the identical payload rather than providing distinct test data.

### 3.2 Response

```json
{
  "status": "00",
  "message": "Successful",
  "data": {
    "valid": true,
    "idNumber": "FFF39140AA98",
    "gender": "male",
    "fullName": "Andrew Smith Doe",
    "firstName": "Andrew",
    "lastName": "Doe",
    "middleName": "Smith",
    "dateOfBirth": "1960-10-31",
    "residentialAddress": "13, Newton Street, Ikeja, Lagos",
    "expiryDate": "27-11-2027",
    "photo": "base64 image string",
    "stateOfOrigin": "",
    "stateOfResidence": "",
    "watchListed": "",
    "levelOfAccount": "",
    "nationality": "",
    "enrolmentBank": "",
    "enrolmentBranch": "",
    "registrationDate": "",
    "nin": "",
    "available": true,
    "firstNameMatch": true,
    "lastNameMatch": true,
    "dobMatch": true
  }
}
```

**Observation:** many fields are present but empty in the sample. Whether they are populated in
production is **not documented**. `watchListed`, `levelOfAccount`, `enrolmentBank`, and
`enrolmentBranch` suggest this endpoint returns more than licence validity, but no semantics are given.

**Observation:** `expiryDate` is `DD-MM-YYYY`, while `dateOfBirth` is `YYYY-MM-DD`. The response mixes
formats.

**Not documented:** error responses, invalid-licence response, photo format, rate limits, or the
meaning of `available`.

## 4. Image match verification

**Path:** `/image/match`
**Method:** `POST`
**Description:** compares an uploaded image with the image on the customer's BVN.

### 4.1 Request

```json
{
  "base64Image": "/9j/4AAQSkZJRgABAQEASABIAAD/4S/SRXhpZgAATU0AKgAAAAgACwALAAIAAAAmAAAIngESA.....",
  "bvn": "22222222252"
}
```

| Field | Description | Required |
| --- | --- | --- |
| `base64Image` | Image to evaluate, base64-encoded. | Mandatory |
| `bvn` | Customer's BVN. | Mandatory |

**Confirmed:** the image must be `.jpg`, `.jpeg`, or `.png`.

**Observation:** the table describes `bvn` with the example value `22222222252` rather than a
description. That is the literal table content.

### 4.2 Response

Matched:

```json
{
  "status": "00",
  "message": "Successful",
  "data": {
    "responseMessage": "Matched image",
    "similarityScore": 99.96447,
    "isMatch": true,
    "bvn": "22222222252"
  }
}
```

Mismatched:

```json
{
  "status": "00",
  "message": "Successful",
  "data": {
    "responseMessage": "Mismatch facial image",
    "similarityScore": 1.3912822,
    "isMatch": false,
    "bvn": "22222222252"
  }
}
```

**Observation:** the envelope `status` is `"00"` and `message` is `"Successful"` even when
`isMatch` is `false`. Callers must inspect `data.isMatch`; the top-level status only says the request
was processed.

**Not documented:** the similarity threshold used by the vendor, whether the caller may choose a
threshold, the score range, error responses, or image size limits.

**Security:** this endpoint combines a biometric image with a BVN. Both are sensitive personal data.
There is no documented liveness binding, so a printed photo could potentially be submitted; use the
separate [liveness check](#5-liveness-check) where a live subject is required.

## 5. Liveness check

**Path:** `/checkliveness`
**Method:** `POST`
**Base URL:** `https://api-devapps.vfdbank.systems/vtech-wallet/api/v2/wallet2` (test) /
`https://api-apps.vfdbank.systems/vtech-wallet/api/v2/wallet2` (live)
**Description:** returns the liveness probability of an image.

### 5.1 Request

```json
{
  "base64Image": "/9j/4AAQSkZJRgABAQEASABIAAD/4S/SRXhpZgAATU0AKgAAAAgACwALAAIAAAAmAAAIngESA....."
}
```

| Field | Description | Required |
| --- | --- | --- |
| `base64Image` | Image to evaluate, base64-encoded. | Mandatory |

### 5.2 Response

```json
{
  "status": "00",
  "message": "Successful",
  "data": {
    "probability": "0.13133287",
    "score": "-1.8892249",
    "quality": "0.30681747"
  }
}
```

| Field | Description |
| --- | --- |
| `probability` | Main decision value. The image is accepted as "live" when probability is **greater than 0.5**. Range 0–1. |
| `score` | For BPCER/APCER tuning; mostly for calibration. Range is unbound. |
| `quality` | Image "goodness". Higher values indicate the image is good enough for liveness checking. |

**Confirmed:** `probability` "should always be used to make a liveness check decision".

**Observation:** the values are **strings**, not numbers. Convert them before comparison; string
comparison of `"0.13133287"` would be wrong.

**Observation:** the sample's `probability` (0.13) is below 0.5 and would be rejected, even though the
envelope says `"Successful"`. This is a processing success, not a liveness pass.

**Not documented:** the accepted `quality` threshold, error responses, retry guidance for low-quality
images, or whether `score` should influence decisions.

### 5.3 Image requirements

The page states that images not meeting these conditions will be rejected.

**Format**

- Supports JPEG, PNG, and BMP in Base64.
- Lossless formats preferred; lossy compression reduces accuracy.
- For JPEG, 70 is the lowest practical compression level.

**Resolution**

- Face should occupy at least 1/4 of the image area.
- Recommended resolution: 600×800 to 960×1280 (portrait orientation).

**Composition**

- Only one main face; fully visible, no occlusion, no crop.
- Small background faces are ignored.
- Minimum face-box size: 150×150 pixels.
- Padding between face box and image borders: at least 15 pixels.
- Distance between pupils: at least 50 pixels.
- Out-of-plane rotation (pitch and yaw): no more than ±30 degrees.

**Accuracy-affecting conditions named by the vendor**

- Motion blur can significantly increase BPCER (genuine person classified as a spoof).
- Texture filtering can significantly increase APCER (impostor allowed through).
- Spotlights on the face or nearby surroundings can increase BPCER.
- Ill-lit environments and coloured light can increase BPCER.
- Fish-eye lenses are not supported.
- Sunglasses may confuse the check.

**Observation:** the document upload page does not repeat these constraints, and the image-match page
only states JPG/JPEG/PNG. The liveness rules are the most detailed image specification in the KYC set.

## 6. NIN verification

**Path:** `/verify/nin`
**Method:** `POST`
**Description:** verifies a National Identification Number.

### 6.1 Request

```json
{
  "idNumber": "11111222221"
}
```

| Field | Description | Required |
| --- | --- | --- |
| `idNumber` | NIN to verify. | Mandatory |

**Observation:** the field is called `idNumber`, not `nin`, unlike the document-upload endpoint which
uses `nin` inside `accountOpeningData`.

### 6.2 Response

```json
{
  "status": "00",
  "message": "Successful",
  "data": {
    "valid": true,
    "idNumber": "45629461922",
    "gender": "m",
    "phoneNumber": "08132741111",
    "fullName": "Jude Paul Thomas",
    "firstName": "Jude",
    "lastName": "Thomas",
    "middleName": "Paul",
    "dateOfBirth": "1997-10-20",
    "address": "Not Available",
    "expiryDate": "Not Available",
    "photo": "base64 image string",
    "available": true,
    "firstNameMatch": false,
    "lastNameMatch": false,
    "dobMatch": false
  }
}
```

**Observation — inconsistency:** the request sends `11111222221`, but the response returns
`45629461922`. Either the sample is inconsistent or the API substitutes a stored NIN. Do not assume the
response `idNumber` equals the request.

**Observation:** `firstNameMatch`, `lastNameMatch`, and `dobMatch` are all `false`, yet `fullName`
and `dateOfBirth` are populated. The comparison basis is not documented: there is no name or date of
birth in the request to compare against. These flags may be meaningless for this endpoint or may
compare against a stored profile.

**Observation:** `gender` is `"m"` here, while driver licence returns `"male"`.

**Not documented:** invalid-NIN response, `available` semantics, photo format, whether `address` and
`expiryDate` can contain real values, or error codes.

## 7. Cross-endpoint observations

| Theme | Finding |
| --- | --- |
| Envelope | Four endpoints use `status`/`message`/`data`; AML uses `responseCode`/`hasError`/`message`/`data`. |
| Success code | Four use `"00"`; AML uses `data.status: "200"`. |
| False result | Image match and NIN can return `status: "00"` with a negative result. Inspect the data. |
| Dates | AML `DD-Mon-YYYY`; Driver License request `YYYY-MM-DD` and response expiry `DD-MM-YYYY`; NIN `YYYY-MM-DD`. |
| Field casing | `firstname` (AML) vs `firstName` (Driver License, NIN). |
| Base URL | Liveness uses the wallet base; the other four use the KYC base. |
| Test data | Only Driver License provides test data, and it duplicates the sample. |
| Errors | No endpoint in this set publishes an error catalogue. |
| HTTP status | Not documented for any endpoint. |

## 8. Security notes

- **Biometric data.** Image match and liveness accept facial images. NIN and driver licence return
  photos. These are sensitive personal data under the Nigeria Data Protection Act and comparable
  regimes; retention, consent, and transfer basis need legal review.
- **BVN/NIN handling.** Image match takes a BVN; NIN verification takes a NIN. Both are high-value
  identifiers. The pages give no masking, hashing, or logging guidance.
- **Base64 over JSON.** Images are sent inline, so they can appear in request logs, APM traces, and
  error reports unless redacted.
- **No documented liveness binding.** Image match does not state that it checks liveness. Use the
  liveness endpoint and a documented threshold, or confirm with PSL that image match is spoof-resistant.
- **AML result opacity.** The AML endpoint's response does not expose a screening decision. A
  compliance process cannot rely on "Data added successfully" as a pass.
- **PII in responses.** Driver licence and NIN return address, date of birth, photo, and other identity
  data. Treat responses as regulated personal data.
- **No rate-limit documentation.** Enumeration protection is not described.
