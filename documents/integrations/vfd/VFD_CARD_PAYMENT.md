# VFD Card Payment API

> **Source:** [Card Payment](https://vbaas-docs.vfdtech.ng/docs/wallets-api/Products/card-api)
> **Retrieved:** 6 November 2026. **Documentation only.**
>
> The vendor describes these APIs as enabling card-payment functionality. The only payment flow
> documented on this page is **non-tokenized**: the payer enters full card details for each payment.

---

## 1. Authorization and base URL

**Authorization:** `AccessToken: {{token}}`. See [VFD_AUTHENTICATION.md](VFD_AUTHENTICATION.md).

| Environment | Base URL |
| --- | --- |
| Test | `https://api-devapps.vfdbank.systems/vtech-cards/api/v2/baas-cards` |
| Live | `https://api-apps.vfdbank.systems/vtech-cards/api/v2/baas-cards` |

All paths below are relative to this base URL.

## 2. Notifications

A webhook must be configured on the BaaS portal to receive successful card-transaction notifications.
The documentation says the webhook must be shared for both test and production environments, uses
HTTP `POST`, and receives this payload:

```json
{
  "status": "00",
  "message": "Success",
  "data": {
    "reference": "rosapay-01919",
    "paymentReference": "202405020958548EOVV",
    "amountCollected": "990",
    "amountCredited": "985"
  }
}
```

| Field | Description |
| --- | --- |
| `reference` | The unique reference supplied when making the card payment. |
| `paymentReference` | Generated by VFD; identifies the card transaction. |
| `amountCollected` | Amount collected by VFD. |
| `amountCredited` | Amount credited to the collections account. |

**Vendor security advice:** IP whitelisting is advised when sharing the webhook. Unlike the wallet
webhook page, this page does not state that a `200` response is required, and it does not define a
signature.

Full webhook context: [VFD_WEBHOOKS.md](VFD_WEBHOOKS.md) §6.

## 3. Payment options documented

The page says “You have an option for card payments”, then lists only:

1. **NON-TOKENIZED CARD PAYMENT** — the payer fills all card details to make a payment.

**Not documented:** tokenized/saved-card payments, recurring card charges, card-on-file, 3-D Secure
merchant configuration, refunds, void, partial capture, or card verification-only operations.

---

## 4. Non-tokenized card flow

1. Configure the card-payment webhook on the BaaS portal.
2. Call **Initiate Non-Tokenized Payment**.
3. Branch on the response:
   - **If `redirectHtml` is present:** redirect the payer to that HTML/URL and let them follow the
     displayed instructions to complete payment.
   - **If `redirectHtml` is absent:** the payer receives an OTP. Build an OTP entry page and call
     **Validate OTP**. If the OTP is valid, the payment is complete.
4. Call **Payment Status** to confirm the final status.

**Observation:** the documented response containing `redirectHtml` also has
`data.code: "03"` and `serviceResponseCodes: "COMPLETED"`. Those values sit alongside an instruction
to authenticate the payer; the page does not explain the apparent contradiction. Treat the presence
of `redirectHtml` as the branch condition, as the vendor instructs.

## 5. Initiate non-tokenized payment

**Path:** `/initiate/payment`
**Method:** `POST`

### Sample request

```json
{
  "amount": "1000",
  "reference": "rosapay-01919",
  "useExistingCard": false,
  "cardNumber": "5060990580000217499",
  "cardPin": "1111",
  "cvv2": "111",
  "expiryDate": "0350",
  "narration": "Payment for electronics",
  "customerId": "test@gmail.com"
}
```

### Request fields

| Field | Required | Description |
| --- | --- | --- |
| `amount` | Mandatory | Amount to debit in naira. Minimum is ₦1,000. |
| `reference` | Mandatory | Unique transaction reference, prefixed with the wallet name, e.g. `rosapay-01919`. |
| `useExistingCard` | Mandatory | “Should always be false” for this flow. |
| `cardNumber` | Mandatory | Card number. |
| `cardPin` | Mandatory | Card PIN. |
| `cvv2` | Mandatory | Card CVV2. |
| `expiryDate` | Mandatory | Card expiry in `MMYY` format, e.g. `0350`. |
| `narration` | Optional | Description of the payment purpose. |
| `customerId` | Mandatory | Unique customer identifier, e.g. the customer's email. |

### Response with redirect HTML

```json
{
  "success": true,
  "data": {
    "code": "03",
    "serviceResponseCodes": "COMPLETED",
    "redirectHtml": "https://api-devapps.vfdbank.systems/vtech-cards/api/v2/baas-cards/initiate-3ds?adviceReference=OdTechWallet-2026102016215&clientLogo=",
    "narration": "Proceed to authenticate payer"
  },
  "message": "Proceed to authenticate payer"
}
```

### Response without redirect HTML

```json
{
  "success": true,
  "data": {
    "currency": "NGN",
    "amount": 500.00,
    "merchantReference": "ISW-BaaSTest-2026101322037",
    "paymentId": "3081353715",
    "authType": "OTP"
  },
  "message": "Kindly enter the OTP sent to **********8904 and s***************@yahoo.com"
}
```

**Observation:** the example without redirect shows `amount: 500.00`, although the request minimum is
stated as ₦1,000. The response is an example, not necessarily paired with the request above. Do not
infer that ₦500 is accepted.

**Observation:** the OTP-delivery message masks the phone and email, but the documentation does not
specify whether these are the cardholder's registered contacts or the `customerId` supplied.

## 7. Validate OTP

**Path:** `/validate-otp`
**Method:** `POST`

**Description:** validates the OTP received by the customer. If valid, the payment is completed.

### Sample request

```json
{
  "otp": "123456",
  "reference": "rosapay-01919"
}
```

| Field | Required | Description |
| --- | --- | --- |
| `otp` | Mandatory | OTP received by the customer. |
| `reference` | Mandatory | Must be the same reference sent to `/initiate/payment`. |

### Sample response

```json
{
  "status": "00",
  "message": "Success",
  "data": {
    "reference": "rosapay-01919"
  }
}
```

> **Not documented:** invalid/expired OTP responses, retry limits, or OTP resend.

## 8. Payment status

**Path:** `/payment-details?reference={reference}`

**Method:** **not documented.** The page gives only the API context, description and query parameter.

**Description:** confirms a payment status.

| Query | Required | Description |
| --- | --- | --- |
| `reference` | Mandatory | Unique reference supplied when making the card payment. |

### Sample response

```json
{
  "status": "00",
  "message": "Successful Transaction Retrieval",
  "data": {
    "transactionStatus": "00",
    "transactionMessage": "SUCCESS",
    "amount": "1000.00",
    "reference": "AdminTest-0995999980",
    "transactionDescription": "Request successfully treated"
  }
}
```

> **Ambiguity:** the method is absent. Given the query-string shape, `GET` is plausible, but the
> vendor documentation does not state it. Confirm in sandbox or with PSL before implementing.

## 9. Response codes

**Not documented:** this page publishes no response-code table. The visible values are:

| Location | Value | Meaning in context |
| --- | --- | --- |
| Initiate data | `code: "03"` | Shown with `redirectHtml` and “Proceed to authenticate payer” |
| Initiate data | `serviceResponseCodes: "COMPLETED"` | Shown with redirect flow |
| Initiate data | `authType: "OTP"` | OTP flow |
| Validate OTP | `status: "00"` | Success |
| Payment status | `transactionStatus: "00"` | Success |
| Payment status | `transactionMessage: "SUCCESS"` | Success |

Do not generalise these into a full card error catalogue.

## 10. Security considerations

The documented flow requires the merchant's server or client to handle:

- full **PAN** (`cardNumber`);
- **CVV2**;
- **card PIN**;
- expiry.

This is highly sensitive card data. The vendor documentation does not state PCI-DSS scope, whether
the merchant may transmit these values directly, whether tokenisation is available, or what logging
and retention rules apply. Any Hivorr review must treat this as a blocking security question, not an
implementation detail. See [VFD_INTEGRATION_NOTES.md](VFD_INTEGRATION_NOTES.md).

Other observations:

- The test cards are published sandbox data and must never be used in production.
- The webhook carries `amountCollected` and `amountCredited`; reconciliation must not assume they are
  equal.
- No webhook signature is documented; IP whitelisting is advised but not specified.
