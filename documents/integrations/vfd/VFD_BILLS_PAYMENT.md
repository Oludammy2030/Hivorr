# VFD Bills Payment API

> **Source:** [Bills Payment](https://vbaas-docs.vfdtech.ng/docs/wallets-api/Products/bills-payment-api)
> **Retrieved:** 6 November 2026. **Documentation only.**
>
> The vendor describes this API as a standardised way to integrate bill-payment functionality and
> automate payment processes.

---

## 1. Authorization and base URL

**Authorization:** `AccessToken: {{token}}` on every endpoint. Token generation is documented in
[VFD_AUTHENTICATION.md](VFD_AUTHENTICATION.md).

| Environment | Base URL |
| --- | --- |
| Test | `https://api-devapps.vfdbank.systems/vtech-bills/api/v2/billspaymentstore` |
| Live | `https://api-apps.vfdbank.systems/vtech-bills/api/v2/billspaymentstore` |

All paths below are relative to this base URL.

## 2. Documented flow

1. Call **Biller Category** to get the list of categories.
2. Call **Biller List** with a category name to get billers in that category.
3. Call **Biller Items** for a biller to get its payment items.
4. Optionally or mandatorily (depending on the product) call **Validate Customer** to verify the
   customer identifier that will be used in **Pay Bills**.
5. Call **Pay Bills** with information from the biller list and biller items.
6. Call **Transaction Status** to check payment status.

**Vendor warnings:**

- Customer validation is mandatory for utility and cable TV services and should be done in the live
  environment.
- For data and airtime, customer validation is optional and can be bypassed.
- For utility, cable TV, betting and gaming, customer validation is required before payment.
- For JAMB PIN purchase, use the generated JAMB profile code as the customer ID. The profile code is
  generated by sending `NIN <space> <11-digit NIN>` by SMS to `55019` or `66019` from an active phone
  number with at least ₦50 airtime. The vendor says a unique 10-digit profile code is returned by SMS.

## 3. Biller Category

**Path:** `/billercategory`
**Method:** `GET`

**Description:** returns biller categories.

### Request headers

| Key | Value |
| --- | --- |
| `AccessToken` | `{{token}}` |

### Sample response

```json
{
  "status": "00",
  "message": "Successfully Returned Biller Category",
  "data": [
    { "category": "Airtime" },
    { "category": "Cable TV" },
    { "category": "Data" },
    { "category": "Internet Subscription" },
    { "category": "Utility" }
  ]
}
```

> **Observation:** this is the only documented response. No failure example or HTTP error is shown.

## 4. Biller List

**Path:** `/billerlist?categoryName={categoryName}`
**Method:** `GET`

**Description:** returns billers for a category. If `categoryName` is not passed, billers for all
categories are returned.

### Query parameters

| Field | Required | Description |
| --- | --- | --- |
| `categoryName` | Optional | Filters billers by category. Omitting it returns all categories. |

  "message": "Succesfully Returned Biller list",
  "data": [
    {

      "category": "Airtime"

    {
      "id": "eting",

      "convenienceFee": "30"
    },
    {
      "id": "glong",
      "name": "GLO",

### Documented notes

> Do not assume the category string is normalised; match as returned or confirm with the vendor.

## 6. Validate Customer

**Path:** `/customervalidate`
**Method:** `GET`

Full documented query string:

`/customervalidate?divisionId={divisionId}&paymentItem={paymentItem}&customerId={customerId}&billerId={billerId}`

**Description:** validates the `customerId` input field (for example a meter number) before payment.

### Query parameters

| Field | Required | Description |
| --- | --- | --- |
| `customerId` | Mandatory | Customer ID, e.g. meter number. |
| `divisionId` | Mandatory | Returned from Biller List as `division`. |
| `paymentItem` | Mandatory | Returned from Biller Items as `paymentCode`. |
| `billerId` | Mandatory | Biller ID returned from Biller List. |

### Sample success response

```json
{
  "status": "00",
  "message": "Successfully validated customer",
  "data": {}
}
```

### Sample failed response

```json
{
  "status": "99",
  "message": "Failed validation",
  "data": {}
}
```

## 7. Pay Bills

**Path:** `/pay`
**Method:** `POST`

**Description:** initiates a bill payment.

### Sample request

```json
{
  "customerId": "09071046909",
  "amount": "2150",
  "division": "C",
  "paymentItem": "dstv",
  "productId": "399",
  "billerId": "dstv",
  "reference": "rosapay-1234",
  "phoneNumber": "09000000000"
}
```

### Request fields

| Field | Required | Description |
| --- | --- | --- |
| `customerId` | Mandatory | Customer identifier, e.g. phone number or meter number. |
| `amount` | Mandatory | Bill cost. |
| `division` | Mandatory | Returned from Biller List. |
| `paymentItem` | Mandatory | Returned from Biller Items as `paymentCode`. |
| `productId` | Mandatory | Returned from Biller List as `product`. |
| `billerId` | Mandatory | Biller ID from Biller List. |
| `reference` | Mandatory | Unique transaction reference, prefixed with wallet name or a name of choice, e.g. `rosapay-1234`. |
| `phoneNumber` | Not mandatory | Customer phone number. |

### Sample success response

```json
{
  "status": "00",
  "message": "Successful payment",
  "data": {
    "reference": "rosapay-1234"
  }
}
```

### Sample failed response

```json
{
  "status": "99",
  "message": "Failed Transaction",
  "data": {
    "reference": "rosapay-1234"
  }
}
```

### Documented operational notes

1. **AEDC first-time payments:** two key-change tokens are returned, `KCT1` and `KCT2`. On the meter,
   enter the two KCTs one at a time, followed by the third token, which is the energy-credit token.
2. **IKEDC:** customer phone number is mandatory.
3. **IBEDC Band A:** minimum vending amount is NGN 5,000. Transactions below this amount will not
   process successfully.

> **Not documented:** how `KCT1`/`KCT2` appear in the JSON response. The sample success response only
> contains `reference`; the notes describe token behaviour but not the response field names. Manual
> verification is required before relying on token delivery.

## 8. Transaction Status

**Path:** `/transactionStatus?transactionId={transactionId}`
**Method:** `GET`

**Description:** returns the status of a bill payment.

### Query parameters

| Field | Required | Description |
| --- | --- | --- |
| `transactionId` | Mandatory | Transaction reference. |

### Sample response

```json
{
  "status": "00",
  "message": "Successful Transaction Retrieval",
  "data": {
    "transactionStatus": "00",
    "amount": "500",
    "token": ""
  }
}
```

### Sample not-found response

```json
{
  "status": "108",
  "message": "No Transaction!"
}
```

> **Observation:** `data.token` is where a prepaid token would plausibly appear, but the documentation
> does not define it. Do not assume it contains KCT/energy tokens without sandbox evidence.

---

## 9. Response codes

| Code | Description | Reversal instruction |
| --- | --- | --- |
| `00` | Successful | No Reversal |
| `09` | Pending | No Reversal |
| `99` | Failed | Reversal |

**Observation:** the page does not map these codes to HTTP statuses, and does not publish codes for
validation failures beyond `99`. The not-found code `108` is shown in the status endpoint but is not
in the code table.
